# 首页互动回复提醒设计

**日期：** 2026-08-18

**状态：** 已实施，收尾集成

**范围：** 首页“水帖”信息流（当前排序模式）、回复通知查询与已读消费、BottomSheet 渐进披露、帖子详情页的未读提示清理。

---

## 1. 问题与目标

当前用户只有进入具体帖子后，才会看到“未读回复”横幅。用户在首页无法发现自己的帖子或评论被回复，导致回复容易被遗漏。

本设计将提醒前移到首页信息流，使用户能在首页直接看到：

- 有多少条未读互动回复；
- 有未读互动回复这一状态，并能点击进入处理。

点击后仍进入原帖并定位目标回复。帖子详情页不再显示“有新回复”提示，避免同一未读状态在两个页面重复出现。

## 2. 已确认方案

采用“首页信息流顶部互动模块”。模块位于“水帖”页当前排序模式的搜索框下方、首个帖子卡片之前；用户停留在“综合”等模式时也必须可见。

当存在未读回复时，模块包含：

```text
● 🗨 互动回复    N 条新回复  >
```

- **首页入口**：仅显示互动类型与未读总数（中性 surfaceContainerLow 底色 + brandPrimary 点缀），不显示回复人、回复内容或帖子标题，保持首页信息流紧凑干净。
- **BottomSheet 渐进披露**：有多条未读时，点击模块打开未读回复列表，完整展示发送者头像、昵称、回复正文摘要（最多2行）、原帖标题（`回复于《...》`）及相对时间。
- **单条未读**：仅一条未读时，点击模块直接打开该回复所在原帖。
- **首页展示提醒本身不改变已读状态**。

未采用的方案：

| 方案 | 不采用原因 |
| --- | --- |
| 顶部栏仅红点或数量入口 | 入口缺少明确的互动类型和可发现的点击区域。 |
| 仅在自己的帖子卡片上标注 | 原帖不在当前信息流时会遗漏；也无法覆盖“回复我的评论”。 |

## 3. 交互与未读合同

```text
首页加载未读摘要
  -> 显示模块（不标记已读）
  -> 点击单条回复 / 从多条列表中选择一条
  -> 成功取得原帖后，仅标记该通知已读
  -> 打开帖子详情并定位 targetReplyId
  -> 返回首页后刷新模块
```

### 3.1 多条回复与渐进披露

- 主页模块仅显示类型图标与总数。
- 点击模块时，若未读数大于 1，弹出仅包含未读回复的 BottomSheet 列表。
- 列表项展示发送者头像（`CachedAvatar`）、昵称、回复摘要、原帖标题和相对时间。
- 当 `totalCount > items.length`（如服务端最多返回 20 条，实际总数 37 条）时，Sheet 标题显示 `未读回复 37 最近 20 条`。
- 点击列表项只消费该项；其余项目保持未读并继续显示在首页模块中。
- 不提供“查看首页模块即全部已读”或“全部标记已读”操作。

### 3.2 跳转与已读时机

- 跳转使用现有 `buildPostDetailRoute(post, targetReplyId: relatedId)`，复用详情页的目标回复定位能力。
- 客户端先拉取原帖。原帖可打开后，再调用现有 `POST /notifications/read-selected` 标记所选通知。
- 原帖被删除（404）时，客户端主动向服务端调用 `markRead(item.id)` 消费该通知。成功后本地移除该死提醒并提示“原帖已删除，已移除提醒”；若消费失败则保留提醒并提示“原帖已删除，但提醒清理失败”。
- 读接口、跳转或已读请求失败时，用户可继续浏览首页；已成功获取的未读条目不得被本地静默清空（保持内容稳定性）。

### 3.3 帖子详情页

删除以下仅服务于“详情页发现未读回复”的行为：

- `GET /posts/:id/notifications/unread` 请求；
- 未读回复横幅；
- 未读回复 BottomSheet；
- 详情页内的“全部标记已读”操作。

保留详情页的正常评论加载、评论排序、`targetReplyId` 锚点定位和回复发送能力。

## 4. 服务端合同

新增一个只返回当前登录用户未读回复的接口：

```text
GET /notifications/replies/unread?limit=20
```

接口要求：

- 强制以认证用户作为 `user_id`；不得接受客户端传入的用户 ID。
- 仅查询 `type = reply` 且 `is_read = false` 的通知。
- 按 `created_at DESC` 排序，并限制最大条数，避免首页请求无界增长。
- 返回通知 ID、帖子 ID、目标回复 ID、通知内容、创建时间、发送者基础资料和原帖标题。
- 发送者和帖子信息使用批量查询，禁止按通知逐条查询造成 N+1。
- 无未读时返回稳定空数组和 `count: 0`，不以 404 表示空态。

已读操作继续复用现有接口：

```text
POST /notifications/read-selected
{ "ids": [notificationId] }
```

该接口已有“当前用户 + 指定 ID”约束，首页只能提交用户自己收到的通知 ID。

## 5. 客户端边界

| 单元 | 职责 |
| --- | --- |
| `UnreadReplyNotification` | 承载未读回复数据，包含发送者、回复正文、原帖标题等字段。 |
| `ReplyNotificationService` | 请求首页未读摘要、补充标题兼容、调用选中通知的已读接口。 |
| `ReplyNotificationReminder` | 首页紧凑提醒条与 BottomSheet 列表渲染。 |
| `ShuitieScreen` | 管理首页模块的加载、自动轮询、刷新容错、死提醒清理与跳转。 |
| `PostDetailScreen` | 仅消费外部传入的目标回复 ID，不再自行查询或展示未读提醒。 |

## 6. 状态矩阵

| 状态 | 首页模块 | 用户操作 |
| --- | --- | --- |
| 未登录 | 不渲染 | 无请求。 |
| 加载中 | 不渲染额外骨架 | 首页帖子流正常可用。 |
| 无未读 | 不渲染 | 无。 |
| 一条未读 | 展示紧凑入口 | 点击后直接打开原帖并定位回复。 |
| 多条未读 | 展示紧凑总数 | 点击后弹出 BottomSheet 挑选具体回复。 |
| 首次请求失败 | 静默不渲染 | 保持空状态，下次触发时重试。 |
| 已有数据后刷新失败 | 保留旧数据（Content Stability） | 不闪退、不清空已有提醒。 |
| 60 秒自动刷新 | 后台轮询更新未读数 | 停留首页时新回复可及时出现。 |
| 原帖已删除 (404) | 触发 markRead 成功后移除 | 显示“原帖已删除，已移除提醒”。 |
| 已读请求失败 | 保留本地未读条目 | 不移除、不误导用户。 |

## 7. 视觉、动效与无障碍

- 使用现有 surfaceContainerLow 中性底色与细边框，图标与小圆点使用 `AppColors.brandPrimary`。
- 模块高度不超过 48px，点击目标符合 44 × 44 logical px，并提供完整语义标签。
- BottomSheet 内展示完整上下文（头像、昵称、摘要、原帖标题、时间）。
- 支持深色模式与 1.3 倍文字；长回复与原帖标题均截断而不遮挡数量或跳转提示。
- 不添加自动展开、列表 stagger 或其他装饰性动画；仅保留 Material 按压反馈。

## 8. 验收与测试

服务端：
- 未读接口只返回认证用户的 `reply` 通知，忽略已读和其他通知类型；
- 排序、最大条数、原帖标题和发送者批量映射正确；
- 边界条件与无未读稳定空态测试通过。

客户端：
- 单条与多条未读在首页均表现为紧凑入口；
- BottomSheet 完整渲染回复者头像、昵称、内容、原帖标题和相对时间；
- 首次失败不展示，已有提醒后刷新失败保留旧提醒；
- 404 原帖自动触发 markRead 并在成功后清理本地死提醒；
- 60 秒自动刷新包含未读回复检查；
- 详情页不再请求帖子内未读接口，也不渲染未读横幅；
- 覆盖浅色、深色和 1.3 倍文字布局无 overflow。
