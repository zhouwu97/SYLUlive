# 原教务绑定自动登记测试

只使用原来的教务连接／绑定入口，没有新增学生绑定或单独认证入口。

## 链路

1. 在原教务入口选择已有教务类型并登录学校，密码仍由本机直连学校使用。
2. 本机登录成功后检查服务器可信身份；已有匹配身份时直接保留，不重复发送学校会话。
3. 记录缺失时先完成账号配置对账，再临时发送当前学校 Cookie／必要会话前缀。
4. 服务器重新请求固定学校本人资料入口核对学号；核对一致才登记可信身份并刷新 App 资料。
5. 旧设备已有本机绑定但服务器漏记时，恢复会话、刷新课表或自动重试会走同一补交流程。只有过期本机标记、没有有效学校会话时不能授予资格。
6. 进入试卷库时先刷新服务器资料；仍缺记录则沿用同一会话补交，再刷新准入状态。同步失败可查看原因并重试，继续使用原教务入口恢复过期会话。

## 验收

- 原入口本科登录成功后自动登记；研究生继续原验证码流程，不增加入口。
- 已有可信身份不要求重复绑定；本机 declared/bound/verified 标记不能掩盖服务器缺失。
- 服务器无记录时刷新课表可自动补交；断网仍可本机使用，恢复后重试。
- 错误密码、过期 Cookie、伪造 verified、错误学号和自定义 URL 都不能授予资格。
- 云端解绑、换绑、账号切换、撤销授权期间，迟到请求不能恢复旧身份。
- 普通资料刷新不能被当成切号并反复启动同步；同一账号退出重登后，旧登录会话的返回值也不能覆盖新会话。
- 必须在真实 MyApp 装配下验证会话代次读取和核验完成后的资料刷新回调，避免只测独立客户端而漏掉 Provider 作用域错误。
- 重复请求只保留同一条绑定；限流后退避，不无限提交。
- 集市不再将身份缺失说成毕业，使用教务绑定同步状态提示。

端到端测试要求同时部署新增 Go `/api/student-identity/verify-session` 和 Python 内部 `/api/edu/verify_session`。仅安装 APK 无法让旧服务器具备新核验能力。生产部署和真实账号验收必须单独记录，不能将本地测试当作线上修复。
