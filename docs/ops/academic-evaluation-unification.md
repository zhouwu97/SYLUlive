# 学科评价历史主记录统一

设计决策见 [ADR 003](../design/adr/003-academic-evaluation-authority.md)。本工具不创建新业务表，不删除公开评价，不重编号，不截断评论，不修改投票或举报。它把历史教师评价关联到唯一可编辑主记录；已有明确双向关联且正文一致的记录不会再创建副本。

## 执行边界

属于 R3 数据迁移。必须取得明确的生产迁移与发布授权，先备份数据库和当前运行二进制，固定实际生产提交再形成候选，按 [DEPLOY.md](../../DEPLOY.md) 和发布门禁执行。不要从混杂工作区直接构建部署，不用旧基线覆盖线上新增功能。

仅在当前生产已具有课程评价基础表后运行。命令只使用显式 `DSN` 环境变量，不读取默认数据库、不执行 AutoMigrate；凭据通过既有受限环境注入，不写入命令行或报告。Windows/SQLite 默认以只读模式打开已存在文件；正式生产使用 PostgreSQL。报告仅含数量、冲突 ID、原因与指纹，仍需作为受限运维记录保存。

## 发布顺序

新客户端读取 `include_teacher_ratings=true`；迁移未完成时服务端返回“历史评价尚未完成统一迁移”，不会再把两套存储拼成一份列表。因此必须按以下顺序发布：

1. 先发布带双向关联字段的服务端版本（启动迁移增加关联列）。旧客户端不传增强参数，继续读取原课程提交，行为不变。
2. 服务端发布后、客户端放量前完成只读预览、备份和执行迁移，并重新预览确认 `create=0`、`repair=0`。
3. 再发布读取主记录的新客户端；客户端不再按来源分叉读取或编辑。

不要先放量新客户端再补迁移，否则“学科评价”会停留在“迁移未完成”的错误态。

## 预览与执行

在 `server/` 构建或运行：

```bash
go run ./cmd/unify_academic_evaluations
```

这是只读预览。检查 `create`、`repair`、`already_unified`、`conflicts` 与 `fingerprint`。已删除公开评价不会复活。教师缺失、跨用户关联、同目标多个历史记录、已存在不同正文/星级或未完成审核的冲突均阻止执行，不按更新时间猜测覆盖。

确认备份可恢复、冲突为零并暂停相关写入后，使用刚确认的指纹：

```bash
go run ./cmd/unify_academic_evaluations \
  --apply --backup-confirmed --expected-plan <fingerprint>
```

执行在一个事务内重新预览并校验指纹；PostgreSQL 对相关三表使用短锁等待。指纹不一致、锁超时或任一步写入失败时整批回滚。执行成功后重新预览应为 `create=0`、`repair=0`，仅有 `already_unified`。不要重复使用旧指纹强行执行。

## 验收与恢复

1. 迁移前后核对公开评价总数、ID、星级、正文、原创建/更新时间、治理状态及投票/举报计数；除双向关联外原公开行不变。
2. 同一登录账号：教师详情中的本人评价应在“我的内容 → 学科评价”出现一次；页签数量与个人中心四类内容总数一致。
3. 从教师入口编辑、从课表入口再次编辑，应更新同一个主记录 ID、递增同一 revision，并保留公开评价 ID；旧 revision 更新返回冲突。
4. 删除本人评价后主记录与公开展示同时消失，计数减少；他人或匿名删除应失败且不得修改关联。写入失败时两侧都回滚。
5. 验证老客户端和不带增强参数的本人接口可读取同一批主记录；坏游标与旧混合游标可通过重新读取首页恢复。

失败事务无需数据回滚。成功迁移保留旧公开行及全部内容，应用回退保留新增主记录与关系；不要在已有新编辑后恢复整库或删除迁移主记录。发生异常先停写，保存受限预览与执行记录，再按 ID 审核修复；库备份仅用于确认可接受的数据恢复窗口。
