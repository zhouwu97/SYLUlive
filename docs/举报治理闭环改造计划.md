# SYLUlive 举报治理闭环改造计划

## 1. 改造目标

当前举报系统不能只做到：

```text
用户举报
→ 管理员处理
→ 帖子消失
```

需要形成完整的用户闭环：

```text
用户举报帖子
        ↓
管理员审核举报
        ↓
举报不成立 ─────────────→ 结束，不影响帖子
        ↓
举报成立
        ↓
帖子进入治理隐藏状态
        ↓
通知帖子作者
        ↓
作者点击通知
        ↓
进入自己的被处理帖子
        ↓
查看处理原因
   ┌────┴────┐
   ↓         ↓
编辑整改     提交申诉
   ↓         ↓
整改复审     申诉复核
   └────┬────┘
        ↓
管理员审核
   ┌────┴────┐
   ↓         ↓
恢复公开     维持限制
```

最终必须满足：

> 被管理员处理的帖子对普通用户不可见，但作者本人和管理员仍然能够访问。

同时作者必须知道：

* 哪一条帖子被处理；
* 为什么被处理；
* 什么时候被处理；
* 当前是什么状态；
* 能否修改；
* 能否申诉；
* 修改后怎样恢复；
* 申诉后当前进度；
* 最终管理员给出的结果。

---

# 2. 本次改造范围

本轮只改举报治理相关链路，不对社区模块做无关重构。

涉及：

```text
举报系统
帖子状态
帖子详情接口
帖子编辑接口
帖子公共查询
通知系统
通知跳转
帖子详情 UI
我的帖子
申诉系统
管理员举报处理
管理员申诉审核
帖子恢复机制
附件访问控制
相关缓存
```

现有：

* Report 举报体系；
* Notification 通知体系；
* Appeal 申诉体系；
* 帖子删除机制；

尽可能复用。

---

# 3. 最重要的设计原则

必须彻底区分下面两件事：

### 用户自己删除帖子

```text
deleted
```

表示：

> 作者主动删除，该帖子不再作为正常内容存在。

### 管理员治理隐藏

新增：

```text
moderated_hidden
```

表示：

> 内容仍然存在，但由于社区治理原因停止公开展示。

两者不能继续共用 `deleted`。

否则就无法实现：

```text
管理员处理
→ 作者还能查看
→ 作者整改
→ 作者申诉
→ 管理员恢复
```

---

# 4. 帖子状态设计

第一阶段不要引入特别复杂的状态机。

推荐保留现有状态，并新增：

```text
normal
moderated_hidden
deleted
```

含义如下。

| 状态                 | 含义        | 普通用户 |          作者 |      管理员 |
| ------------------ | --------- | ---: | ----------: | -------: |
| `normal`           | 正常帖子      |   可见 |          可见 |       可见 |
| `moderated_hidden` | 治理隐藏      |  不可见 |          可见 |       可见 |
| `deleted`          | 作者删除/永久删除 |  不可见 | 不通过正常帖子接口访问 | 后台审计记录可查 |

不要再增加：

```text
appealing
reviewing
edited
```

之类帖子状态。

申诉状态和整改复审状态应该放到对应业务记录里，不污染 Post 状态。

这样帖子状态始终只描述：

> **这篇帖子现在能不能公开展示。**

---

# 5. 举报处理结果设计

管理员处理举报时至少支持三类结果：

```text
举报不成立
警告/记录，但不隐藏帖子
举报成立并隐藏帖子
```

后续如果确实有需求，再增加严重违规永久删除。

管理员处理界面建议：

```text
举报内容

举报类型：
攻击 / 引战 / 广告 / 色情 / 欺诈 / 其他

举报说明：
xxxxxxxx

被举报帖子：
[帖子预览]

管理员处理：
○ 举报不成立
○ 警告作者
● 限制帖子公开展示

违规规则：
[社区规范条款]

给作者的处理说明：
[                               ]

[确认处理]
```

其中：

**举报人的身份不能出现在给作者的处理结果中。**

---

# 6. 管理员处理举报成立

管理员选择：

```text
限制帖子公开展示
```

后端必须在一个事务里完成：

```text
1. 锁定举报记录
2. 确认举报尚未重复处理
3. 获取帖子
4. 保存治理记录
5. Post.status = moderated_hidden
6. 写入处理原因
7. 更新 Report 状态
8. 创建作者通知
9. 提交事务
```

避免出现：

```text
帖子隐藏成功
但是通知没创建
```

或者：

```text
通知发送成功
但帖子状态修改失败
```

---

# 7. 治理记录

举报记录负责描述：

> 谁举报了什么。

治理记录负责描述：

> 管理员最终对内容做了什么。

如果目前 `Report` 已经完整保存：

```text
target_id
target_type
handled_by
handled_at
decision
reason
action
```

可以直接扩展现有表。

如果现有 Report 无法完整记录治理动作，再增加轻量治理记录。

推荐逻辑字段：

```text
PostModerationRecord

id
post_id
author_id

source_report_id

action
rule_code
reason

operator_id

post_revision

created_at
restored_at
```

其中 `post_revision` 很重要。

因为：

```text
管理员处理的是版本 A
作者后来修改为版本 B
```

未来审核申诉时不能把版本 B 当作原始处罚内容。

---

# 8. 帖子版本号

建议 Post 增加：

```text
revision
```

创建帖子：

```text
revision = 1
```

每次作者编辑：

```text
revision++
```

治理处理时记录：

```text
moderated_revision = 5
```

作者修改以后可能变成：

```text
revision = 6
```

这样后台明确知道：

> 用户已经对违规内容进行了修改。

后续整改复审也可以记录：

```text
submitted_revision = 6
```

避免审核过程中用户修改内容造成竞态。

---

# 9. 帖子读取权限

这是本次后端最重要的一处修改。

对于：

```http
GET /posts/:id
```

不能再简单：

```text
status != normal
→ 404
```

应该变成：

```text
normal
→ 正常读取

moderated_hidden
→ 当前用户 = 作者：允许
→ 当前用户 = 管理员：允许
→ 其他：404

deleted
→ 普通帖子接口统一 404
```

注意其他用户访问治理帖子建议返回：

```http
404
```

而不是：

```http
403
```

不要向其他用户泄露：

> 这条被治理的帖子其实还存在。

必须全面检查所有 Post 查询入口。

包括：

```text
首页
推荐
关注
版块
话题
标签
搜索
排行榜
作者主页
收藏
历史记录
热门
最新评论
分享页
Web 分享落地页
相关推荐
```

公共查询必须明确：

```text
status = normal
```

禁止再写：

```text
status != deleted
```

因为这样会把：

```text

```

泄露出去。

# 11. 作者自己的帖子列表

自己的帖子页面需要区别处理。

作者：

```text
normal
moderated_hidden
```

都可以看到。

例如：

```text
我的帖子

────────────────
校园今天下雪了吗
正常展示

────────────────
关于某某事情……
仅自己可见 · 已被处理
```

治理帖子应该有明显状态标签：

> 已被限制展示

或：

> 仅你和管理员可见

不要使用：

> 已删除

因为帖子并没有删除。

---

# 12. 举报处理通知

管理员处理举报成立以后，必须通知帖子作者。

推荐通知类型：

```text
content_governed
```

payload：

```json
{
  "type": "content_governed",
  "post_id": 123,
  "moderation_id": 456,
  "action": "moderated_hidden"
}
```

通知文案建议：

> **你的帖子已被限制展示**
>
> 你发布的《校园里的某某事情》因违反社区规范，当前已停止公开展示。
>
> 当前仅你和管理员可以查看，你可以查看处理原因、修改内容或提交申诉。

通知中可以显示：

```text
违规类型
处理时间
处理结果
```

但绝对不能显示：

```text
举报人 ID
举报人昵称
举报人头像
举报人联系方式
```

---

# 13. 通知点击跳转

点击治理通知：

```text
通知
↓
post_id
↓
帖子详情
↓
后端识别作者身份
↓
允许读取 moderated_hidden
```

不要专门制造：

```text
/deleted-post-preview
/admin-post-preview
```

这种旁路接口。

帖子仍然使用正常详情页，只是不同权限看到不同状态。

---

# 14. 未登录情况下点击通知

需要考虑：

```text
推送通知
↓
App 当前未登录
↓
进入登录
↓
登录完成
↓
恢复之前 deep link
↓
打开对应帖子
```

不能：

```text
点击通知
→ 被丢到首页
```

建议 deep link 至少保留：

```text
post_id
notification_id
source=moderation
```

# 15. 作者看到的帖子页面

对于：

```text
moderated_hidden
```

帖子详情页顶部增加治理状态卡。

示例：

```text
⚠ 该帖子已被限制展示

该内容目前仅你和管理员可以查看，
不会出现在首页、搜索、个人主页公开区域等位置。

处理原因
违反社区规范：攻击 / 引战

管理员说明
请删除针对具体同学的人身攻击内容后重新提交审核。

处理时间
2026-09-16 10:32

[编辑整改]    [提交申诉]
```

下面继续正常展示原帖：

```text
标题
正文
图片
已有评论
发布时间
```

---

# 16. 治理帖子允许编辑

作者应该可以编辑：

```text
moderated_hidden
```

帖子。

但是必须保证：

> **编辑帖子绝对不能自动恢复公开。**

流程：

```text
moderated_hidden
↓
作者编辑
↓
保存成功
↓
仍然 moderated_hidden
```

禁止出现：

```text
作者修改一个字
↓
status 被编辑接口写回 normal
```

因此必须检查当前 UpdatePost 逻辑。

编辑接口不能通过客户端传入状态：

```json
{
  "status": "normal"
}
```

帖子状态只能由服务端治理逻辑修改。

---

# 17. 编辑后的页面

用户编辑成功以后显示：

```text
✓ 修改已保存

你的修改仅自己和管理员可见，
帖子不会自动恢复公开。

如已完成整改，可以提交管理员复审。

[提交整改复审]
```

---

# 18. 整改复审

建议新增一个非常轻量的整改复审能力。

这和申诉不是一件事情。

整改意味着：

> 我认可内容需要修改，现在已经修改，请重新审核。

申诉意味着：

> 我认为原处罚本身不正确。

两条链路必须分开。

整改：

```text
编辑
↓
提交整改复审
↓
管理员审核修改后的帖子
↓
通过 / 不通过
```

---

# 19. 整改复审数据

可以建立：

```text
PostRectificationReview
```

或者复用现有审核任务体系。

字段只需要：

```text
id
post_id
moderation_id

submitted_revision

status
pending
approved
rejected

reviewer_id
review_reason

created_at
reviewed_at
```

关键是：

```text
submitted_revision
```

管理员审核的是明确版本。

---

# 20. 整改复审提交限制

作者只能对：

```text
moderated_hidden
```

提交整改复审。

并且：

```text
同一帖子只能存在一个 pending 整改申请
```

避免：

```text
用户连续点 20 次
→ 后台出现 20 条任务
```

接口应该幂等处理。

---

# 21. 整改审核通过

管理员确认内容已经整改：

```text
Post.status
moderated_hidden
→ normal
```

同时：

```text
关闭整改任务
写治理恢复记录
通知作者
```

通知：

> **帖子已恢复展示**
>
> 你修改后的《XXXX》已通过复审，现在已恢复正常公开展示。

恢复后：

```text
首页可见
作者主页可见
搜索可见
可评论
可点赞
可收藏
可分享
```

---

# 22. 整改审核不通过

帖子继续：

```text
moderated_hidden
```

通知作者：

> **整改复审未通过**
>
> 当前内容仍存在以下问题：
> XXXXX
>
> 你可以继续修改后再次提交。

# 23. 申诉系统

现有 Appeal 系统直接复用。

不要再创建：

```text
ReportAppeal
PostAppealV2
ModerationAppeal
```

新的平行体系。

申诉记录关联：

```text
moderation_id
post_id
```

作者提交：

```text
申诉理由
补充说明
可选附件
```

# 24. 申诉期间帖子状态

提交申诉：

```text
moderated_hidden
```

不变。

禁止：

```text
提交申诉
→ 自动恢复帖子
```

正确流程：

```text
moderated_hidden
↓
Appeal.pending
↓
管理员重新审核
```

---

# 25. 申诉通过

申诉通过后：

```text
Post.status = normal
```

并记录：

```text
Appeal = approved
ModerationRecord.restored_at
```

作者收到：

> **申诉已通过**
>
> 经复核，《XXXX》的限制已解除，帖子现已恢复正常展示。

---

# 26. 申诉驳回

维持：

```text
moderated_hidden
```

通知：

> **申诉未通过**
>
> 经复核，原处理结果维持不变。
>
> 你仍可以修改帖子后提交整改复审。

这里非常重要。

即使申诉失败：

> 用户仍然应该能够走整改路线。

---

# 27. 编辑和审核并发问题

如果：

```text
作者提交整改 revision=6
↓
管理员正在审核
↓
作者又把帖子编辑成 revision=7
```

管理员不能批准一个自己没有审核的版本。

所以审批时验证：

```text
Post.revision == submitted_revision
```

如果不一致：

```text
409 CONTENT_CHANGED
```

后台提示：

> 作者在审核期间修改了内容，请重新检查最新版本。

整改任务可以：

```text
标记 obsolete
```

或者直接要求重新提交。

---

# 28. 申诉时的内容版本

治理记录必须保存：

```text
处罚时 revision
```

这样管理员审核申诉时至少可以看到：

```text
处罚时内容
当前内容
```

避免出现：

```text
用户把违规内容删掉
↓
管理员看现在没问题
↓
误以为最初处罚错误
```

第一版不用做复杂 diff。

后台只需要：

```text
处理时版本
当前版本
```

分开展示即可。

---

# 29. 治理状态下的评论

推荐：

```text
已有评论：作者和管理员可以查看
新评论：禁止
点赞：禁止
收藏：禁止新增
分享：禁止
```

原因是：

> 帖子已经退出公共社区，不应该继续产生新的互动。

详情页显示：

> 帖子处于限制展示状态，互动功能暂不可用。

---

# 30. 普通用户以前的评论和通知

例如用户 B 以前评论过帖子 A。

帖子被治理后：

```text
B → 我的评论
B → 历史通知
B → 收藏
B → 浏览历史
```

都不能因此重新访问帖子。

点击：

```text
内容暂不可用
```

或者统一：

```text
内容不存在
```

后端依然返回 404。

---

# 31. 分享链接

必须检查：

```text
/posts/:id
Web 分享页
App deep link
```

对于 `moderated_hidden`：

作者：

```text
App 内登录后允许访问
```

管理员：

```text
允许
```

其他用户：

```text
404 / 内容不可用
```

# 32. 图片和附件权限

这是一个容易漏掉的安全点。

如果帖子：

```text
moderated_hidden
```

正文隐藏了，但图片 URL 依然永久公开，例如：

```text
https://xxx.com/uploads/abc.jpg
```

那么严格来说：

> “只有作者能看”并没有真正实现。

需要检查当前帖子附件存储。

如果目前附件本身有鉴权接口，直接跟随 Post 权限。

如果目前是永久公开 URL，至少后续要逐步改成：

```text
media_id
↓
请求资源
↓
检查所属 Post
↓
检查访问权限
↓
返回文件 / 临时 URL
```

第一阶段不必重构全部历史媒体系统，但需要记录为安全项。

## 32.1 实现状态（2026-09-16）

服务端已按「附件本身有鉴权接口，直接跟随 Post 权限」落地：

- 治理隐藏时 `ReconcileFilePublicAccess` 会把没有其他公开引用的文件从
  `public` 降级为 `private`；帖子图片只有 `normal / sold / closed` 状态算公开引用，
  `moderated_hidden` 不算；
- `/uploads/*filepath` 由 `UploadHandler.ServePublic` 提供服务，命中私有文件时走
  `isAuthorizedForPrivateFile`：管理员、以及文件 uploader 本人放行，其余 404；
- 私有响应带 `Cache-Control: private, no-store`，不会被共享缓存长期持有。

客户端补齐（此前缺失，表现为「正文能看、图片全裂」）：

```text
PostMediaAccess.public      → 公开帖子缓存 PostImageCache，无认证头
PostMediaAccess.authorized  → GovernedPostImageCache（账号作用域 key）
                              + Authorization: Bearer <JWT>
                              + 独立 CacheManager
```

- `resolvePostMediaAccess(context, post)` 是唯一判定入口：仅
  `post.isModeratedHidden == true` 且查看者是作者或管理员时切 `authorized`；
- `PostMediaView` 的 `_tile` / 单图 / 进度式缩略图 / 全屏查看器全部透传同一份凭证；
- `AppCachedImage.private` 的既有约束（不得复用公开帖子缓存）继续生效，
  「我的内容」集市封面在治理态改走私有通道；
- 登出 / 换号时由 `AccountSessionCleanupCoordinator` 清空私有缓存。

仍然存在的边界：历史治理帖若在治理前未生成变体，客户端会退回原图请求；
`ImageViewerScreen` 的「查看原图」在鉴权模式下同样走私有缓存，不会写进公开目录。
新治理内容不能通过 API 再泄露附件地址。

# 66. 最终产品形态

完成以后，用户视角应该是这样的：

```text
我的帖子被管理员处理了
        ↓
我明确收到通知
        ↓
我知道哪条帖子出了问题
        ↓
我仍然能够看到自己的内容
        ↓
别人已经无法看到
        ↓
我知道违反了哪条规则
        ↓
我可以修改整改
        │
        ├─→ 修改完成 → 提交复审
        │
        └─→ 不认可处罚 → 提交申诉
                        ↓
                   管理员重新处理
                        ↓
              恢复 / 继续限制
                        ↓
                我收到明确结果
```

核心原则可以最后固定成一句：

> **管理员治理改变的是帖子的公开权限，而不是让作者失去对自己内容的访问权；作者始终拥有知情、整改和申诉入口，恢复公开则必须再次经过服务端审核。**

按这个方案做，现有举报、通知、Appeal 都能继续复用，真正需要新增的核心能力其实只有 **`moderated_hidden`、作者特殊读取权限、整改复审和治理详情 UI**。这样修改范围可控，同时把现在最明显的治理链路断点补完整。
