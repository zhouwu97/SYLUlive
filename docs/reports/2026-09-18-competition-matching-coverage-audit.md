# 竞赛匹配覆盖率审计报告（2026-09-18）

- 输入：`tmp/competition-schedule/public-events.json`（310 条已发布赛事，dataset `2026.07.22-v8.2-activation`）
- 工具：`server/cmd/matchingverify -audit`
- 算法版本：`major-match-v1`
- 上游计划：`docs/plans/competition-recommendation-plan.md` §10.3

## 怎么跑

```powershell
cd server
go run ./cmd/matchingverify -catalog ../tmp/competition-schedule/public-events.json -audit
```

工具**直接调用线上同一份 `competitionmatching` 纯函数包**（词表、解析、打分、排序），
因此报告里的「无映射」「未识别」「宽口径」与线上匹配的口径必然一致——
不存在「离线脚本另写一套逻辑」的漂移。

> 与计划的一处偏差：§10.3 原写「在 `tools/competition_catalog/` 新增 Python 脚本」。
> 实际实现为 Go 子命令。理由是映射表与词表的唯一真源在 `competitionmatching` 包里，
> Python 侧要复现它就必须再抄一份 53 项词表与专业映射，而这正是本次故障的成因之一
> （两处口径各写一份，必然漂移）。报告内容与计划要求的四类输出一致，没有缩水。

## 一、专业簇引用分布（目录侧实际在用）

53 项词表中的 **53 项**都被至少一场赛事引用；引用最多的与最少的差两个数量级：

| 簇 | 引用赛事数 |
|---|---|
| 计算机类 | 81 |
| 工业设计 | 71 |
| 材料类 | 55 |
| 机械类 | 51 |
| 车辆工程 | 48 |
| … | … |
| 交通运输相关 / 化学相关 / 材料成型及控制工程 / 物流管理相关 / 金属材料工程相关 | 各 1 |

**含义**：召回量的差异首先是目录供给的差异，不是算法差异。
「计算机类」专业的学生有 81 条专业直接相关赛事，「物流管理」方向只有 1 条。
这一点已在 `competition-recommendation-algorithm-plan.md` §11.3 被实测证实，
原「四类专业召回量差异 ≤ 30%」的验收指标也因此被替换为「每专业召回下限 ≥ 20」。

## 二、词表收敛与映射缺口

它们**有**专业映射（学生能命中），但目录里可推荐的赛事极少，
属于目录供给问题，不是映射缺口。

## 四、疑似标签错配（须人工复核）

启发式判定：标题命中明确的学科词，而 `eligible_majors` 与预期簇**完全无交集**。
本次共 **4 条**，全部是同一类问题——化工/化学赛事被标成艺术设计类：

| 赛事编号 | 标题 | 现标专业范围 | 预期方向 |
|---|---|---|---|
| NAT-030 | 全国大学生化学实验创新设计大赛 | 视觉传达设计、环境设计、产品设计、动画、工业设计、数字媒体相关 | 化学工程与工艺、应用化学 |
| PROV-030 | 辽宁省大学生化学实验创新设计竞赛 | 同上 | 同上 |
| NAT-065 | 全国大学生化工设计竞赛 | 同上 | 化学工程与工艺、材料类、机械类 |
| PROV-065 | 全国大学生化工设计竞赛（省赛） | 同上 | 同上 |

这与上游计划 §2 P2-8 / D5 记录的现象一致（原记录只有 1 例，本次确认是 **4 条**，
且都是「艺术设计类标签被批量复制到化工赛事」这一种模式，不是零散笔误）。

**修复方式（禁止直接改库）**：
`tools/competition_catalog/export_catalog_v2.py` → 修正 `eligible_majors` →
`validate_catalog_v2.py` → 后台 catalog 的 import → diff 复核 → activate。
改标签会重算 `record_hash` 与 `package_hash`，属于目录重导出，必须与
`personalized_ranking_allowed` 翻转（ADR-002）合并成同一次发布，避免把高风险操作做两遍。

## 七、年级门口径修复（本轮审计发现并已修复的缺陷）

审计追问「被年级门淘汰的 47 条到底是什么赛事」，结果暴露出一个**真缺陷**：

| `eligible_entry_years` 取值 | 赛事数 |
|---|---|
| 研究生 / 已获研究生入学资格的本科生 | 45 |
| 本科生 | **2** |

字段名叫「entry_years」，但线上**全部存的是学历层次**，没有一条是四位年份。
旧门禁拿它和用户的**入学年份**（如 `2023`）做字符串全等比较，于是：

- 45 条「研究生」赛事：本科生被排除 —— 结论正确，但纯属字符串凑巧不相等；
- 2 条「本科生」赛事：**所有本科生都被判为不符** —— 合规用户被淘汰，赛事对任何本科生都不可见。

**修复**：`competitionmatching.ResolveEntryScope` 把该字段解析为两类口径——
学历层次（研究生 / 本科生）与四位年份；门禁按语义比对，两者都支持；
只有口径明确时才允许淘汰，出现**无法识别的取值一律放行**（与「资格类字段只降权不淘汰」一致）。

**修复后实测**（同一份目录快照）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 候选总数（计算机科学与技术） | 263 | **265** |
| 被年级门淘汰 | 47 | **45**（全部为「研究生」类，确属真实不适配） |
| 会计学 `major_match` | 25 | **27** |
| 研究生画像被淘汰 | 47 | **2**（「本科生」类，语义正确） |
| 确定性（5 次复算） | 一致 | 一致 |

「研究生」类赛事对本科生的排除结论不变，但依据从「字符串不相等」变成「学历层次不符」；
原先被误伤的 2 条赛事（会计方向）已恢复可见。无法识别的年级取值清单当前为**空**。

## 八、结论

- 覆盖率侧不存在「某些专业永远匹配不到」的静默缺口：未识别标签 0，无映射专业 0。
- 需要人工处理的具体项只有两类：**4 条标签错配**（化工赛事标成艺术类）与
  **15 个宽口径标签的收敛**，两者都在目录侧，都随下一次目录重导出一起处理。
- 本轮额外发现并修复了一个**年级门口径缺陷**（详见 §七）：2 条赛事此前对全体本科生不可见。
- 报告可在每次目录包发布前重跑，作为发布前检查的一部分。
