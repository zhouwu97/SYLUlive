# Android 发布

本文只描述 Android 发布物的专项执行要求。每次发布先执行根目录 [发布前回归清单](../../RELEASE_CHECKLIST.md)，再按本文完成构建物、设备和渠道验证。

## 1. 构建前

### 更新通道

应用提供 `stable` 正式版更新和独立的 `beta` 测试版下载，完整规则见[应用更新通道契约](../design/app-update-channels.md)。超级管理员在 App“应用版本”或 Web 发布表单选择通道，上传后核对功能说明，再显式发布。

Beta 仅通知在“设置 → 通知与后台”开启测试版通知的用户，说明功能更丰富但不建议小白下载；用户可打开浏览器下载或关闭弹窗。Beta 不进入应用内更新、下载任务或安装器。正式版更新独立检查。分发包的包名、签名和构建号决定用户手动安装的兼容性，不承诺两个通道共存。测试结束可下架全部 Beta，正式通道继续保留回退版本。

上线顺序为服务端、客户端、Beta 记录发布。发布前核验默认用户只收到正式版、订阅用户收到测试版、Beta 仅打开下载链接、关闭／退出订阅、正式最低支持策略，以及真实 Android 浏览器下载。正式版更新继续验收覆盖安装。回退和未验证范围记入当次发布记录。

### 构建准备

- 普通更新保留仍可使用的旧版最低支持构建号。最低支持构建号等于本次最新版时，所有旧版本都会收到强制更新；不要将它作为普通更新的默认填写值。
- 明确版本号、目标 API、发布渠道、服务端契约和兼容范围。
- 固定不可变源代码提交，确认客户端与服务端的实际版本组合。
- 确认 CI 相关 jobs、客户端测试和必要的服务端验证均有可追溯结果。
- 确认正式 API、推送和签名配置来自受控环境；私钥不进入仓库、聊天或构建 artifact。
- 使用 client/scripts/build_release.ps1 或当前仓库批准的正式构建入口，不把临时测试包当正式发布物。
- 正式发布构建设置 RELEASE_DECISION=passed，并提供对应的 CI 运行号和 security.yml 运行号；正式发布固定核验 Gitleaks、govulncheck 和两个 Python pip-audit matrix jobs。脚本会把 workflow_conclusion、evidence_status、Gitleaks 和依赖审计结果写入 release-manifest.json。

## 2. 构建物检查

- 记录 APK／AAB 文件名、版本、源提交、构建时间和 SHA-256。
- 使用 apksigner 验证签名证书指纹与批准记录一致。
- 确认包名、版本号、目标 API、渠道配置和 assetlinks 与发布目标一致。
- 确认构建物未包含调试地址、示例 API、占位推送配置或测试凭据。

## 3. 设备验证

至少在一台目标 Android 设备完成：

- 安装、启动和首次配置；
- 登录、登出、会话恢复和错误提示；
- 本次改动涉及的关键业务链路；
- 权限允许、拒绝和重新授权；
- 网络失败、超时、重试和恢复；
- 覆盖安装、版本升级和旧数据兼容（注意：桌面启动入口自 `MainActivity` 迁至 `.LauncherDefaultStatic` 别名后，部分 Android 启动器在首次跨该边界覆盖升级时会移除原桌面快捷图标，需在版本更新说明中提示用户从应用抽屉重新拖出；后续同架构升级由 `LauncherIconUpdateReceiver` 在后台保持所选图标）；
- 通知、后台恢复和应用重新启动。

验证使用专用测试账号和隔离数据，记录设备、系统、包版本、步骤、结果和脱敏证据。

## 4. 渠道和发布后

- 官网下载地址、GitHub Release、版本更新入口和 assetlinks 指向同一构建物。
- 发布记录包含版本、提交、签名指纹、校验值、验证范围、已知问题和回滚包。
- 发布后按根目录清单完成服务端健康检查、关键业务冒烟和观察窗口。
- 发现阻断问题时停止继续分发，按 docs/ops/rollback.md 和 DEPLOY.md 执行回滚。

签名验证只证明构建物身份，不能替代自动测试、真实设备验证、业务验收或发布批准。
