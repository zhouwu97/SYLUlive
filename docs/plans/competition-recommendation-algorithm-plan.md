## 1. 代码事实基线（已核实，非假设）

在选型之前必须先确认三件事：**有多少数据、有没有标签、房子里的既有惯例是什么**。

### 1.1 规模

| 维度 | 实测 | 来源 |
|---|---|---|
| 已发布赛事 | **310** | `tmp/competition-schedule/public-events.json`（dataset `2026.07.22-v8.2-activation`） |
| 进候选池 | 275 | 同上 |
| 学院 | 13 | `eligible_colleges` 去重 |
| 赛事侧专业标签 | 53（含 15 个模糊标签） | `eligible_majors` 去重 |
| 用户侧专业 | 自由文本，无字典表 | `users.edu_major` |

**这是「几百条物品 × 单个学校的专业目录」的规模，不是电商/内容平台规模。**

### 1.2 标签（训练数据）现状

| 潜在标签 | 现状 | 可用性 |
|---|---|---|
| 曝光 / 点击 / 停留 | **不存在**。全仓检索 `impression` / `exposure` 的命中**全在 Feed 模块**，竞赛模块零埋点 | ✗ 当前不可用 |
| 加入计划 | **存在且已落库**：`user_competition_calendar_items`，`source_type='official'` + `source_event_id` 非空即「从赛事目录加入」 | ✓ 唯一现成的隐式正反馈 |
| AI 推荐快照 | `competition_recommendation_snapshots` 已落库（含 Mode / GroupKey / 匹配维度 / 过期时间） | ✓ 可作行为线索 |
| 竞赛经历 | `user_competition_awards`（含核验状态） | △ 稀疏，只覆盖参赛过的用户 |
| 负反馈 | 不存在 | ✗ |

**结论：当前只有一种可用的隐式反馈（加入计划），且没有曝光分母。
没有分母就无法算 CTR，无法做无偏评估。**

### 1.3 房子里的既有惯例（这是最重要的依据）

Feed 模块已经有完整的推荐演进先例，**竞赛必须对齐它，而不是另起一套 ML 栈**：

| 惯例 | 位置 | 对竞赛的含义 |
|---|---|---|
| 排序器是**纯函数**，不依赖 HTTP/DB | `home_feed_ranker.go:11`「排序器不依赖 HTTP 或数据库」 | 竞赛打分也应做成纯函数包，可单测、可离线复算 |
| **版本化打分函数**（`ScoreHomeFeedCandidate` → `ScoreHomeFeedCandidateV5`） | `home_feed_ranker.go:47,79` | 用 `algorithm_version` 并存新旧打分器 |
| 个性化用**有界增量**，且明确禁止压没公共分 | `home_feed_ranker.go:26-35` `clampPersonalDelta` ±0.20；注释「避免画像把公共质量压没」 | ⚠ 见 §2 决策 D-A：竞赛**不能**照抄这一点，理由见下 |
| 去掉会自我强化的指标 | `home_feed_ranker.go:76-78`「去掉裸 view_count 的正向奖励…后续数据足够后再使用比率」 | 竞赛同理：**不得**把 `competition_rating` 权重做大到能压过专业匹配 |
| 指标按 `algorithm_version` 维度聚合 | `feed_metrics_service.go:65` `impByKind[feed_kind][algorithm_version]` | 竞赛指标必须同样按版本切分，否则调参无依据 |
| 明细 30 天 TTL + 日粒度长期保留 | `feed_impressions` / `feed_daily_metrics`、`feed_metrics_cron.go:17` | 竞赛沿用同一形状 |
| 探索槽固定占比，不参与个性化 | `feed5-personalized-design.md:196-213`：20 条中 3 条（15%），「Explore 不参与 PersonalDelta」 | 竞赛尤其需要，理由见 §7.3 |
| **设计先行 + 门禁 + shadow(percent=0) + 数据达标再灰度** | `feed5-personalized-design.md:290-302`，门禁写为「真实有效曝光 ≥500 + open ≥30」 | 竞赛沿用同一流程与阈值形状 |
| 权重标注为「工程初始值，不是最优值，依赖 Rank Trace 调参」 | `feed5-personalized-design.md:141` | 诚实标注，避免把拍脑袋的权重说成结论 |
| 「不要出现恒为 0 的死分量」 | `feed5-personalized-design.md:85` | 竞赛 P1 不放协同过滤分量 |
| 曝光惩罚只打「多次曝光从未点击」，不搞一刀切 | `feed5-personalized-design.md:189-192` | 竞赛同理，见 §5.4 |

**一句话：仓库里已经有一套经过评审的「启发式 → 埋点 → trace → 调参 → 灰度」的成熟路径。
竞赛复用它，是唯一合理的选择。**

## 2. 关键决策点

### D-A 选型：**不用机器学习模型**，用「规则簇匹配 + 加权线性打分」

**决策：不引入协同过滤、矩阵分解、GBDT、双塔或任何需要训练的模型。**

理由（按重要性排序）：

1. **没有标签，也没有门禁允许我们等。**
   唯一可用的隐式反馈是「加入计划」，且**没有曝光分母**。在没有分母的情况下训练排序模型，
   学到的是「曝光位置的偏差」而不是「用户偏好」。这比规则打分更糟，而且不可解释、不可审计。
2. **物品空间只有 310 条。**
   协同过滤在物品数百级、交互稀疏的场景下，覆盖率会塌缩到头部几十条；
   而竞赛是「机会窗口」型内容（有报名截止），长尾赛事必须能被看到。
   内容基（content-based）方法对每个物品独立打分，**天然没有物品冷启动问题**——
   新赛事一入库就能被正确排序，这是规则法的结构性优势，不是妥协。
3. **治理要求确定性。**
   `docs/competition-catalog-v2-runbook.md` 要求候选顺序可复现、可审计、可回滚。
   一个训练出的模型无法满足「同输入同输出」的强要求（浮点、版本漂移、特征时序）。
   规则打分可以做到字节级复现（`competition-recommendation-plan.md` §10.2 黄金用例）。
4. **驱动本次需求的是「专业匹配」，这是一个领域已知的确定性关系**，
   不是需要从行为里猜的偏好。`标准专业 → 专业簇 → 赛事开放范围` 是学校自己的规则，
   用模型去拟合它属于舍近求远。

**但这不是「永远不做模型」。** 演进路线见 §6.6：
等埋点与 Rank Trace 积累到门禁阈值后，用同一个标签做**权重校准**（逻辑回归 / 小规模 LTR），
而不是替换整个架构。这与 FEED-5 的路径完全一致。

### D-B 排序形态：**专业匹配是主排序键，不是有界增量**

**决策：不采用 Feed 的 `FinalScore = BaseScore × (1 + delta)` 形态，改用可加分的 `match_score` 直接排序。**

这是本方案与 Feed 唯一的实质性背离，必须说明理由：

| | Feed | 竞赛 |
|---|---|---|
| 公共分是什么 | `Quality/HotScore`，由**真实互动**（点赞/回复/活跃）算出，是有意义的质量信号 | `catalog_order` 是**表格行号**，`importance_score` 是人工录入 |
| 公共分可信度 | 高，值得作为排序主体 | 低，不足以作为排序主体 |
| 因此 | 个性化只能是 ±20% 的微调 | 专业相关度必须是主键 |

如果把竞赛也写成「目录序 × (1 + delta)」，那么一个面向「计算机类」的 A 级赛事，
无论学生是机械类还是计算机类，都会稳定排在前面 —— 这正是用户报告的
「不适合我」的现象。所以必须让专业匹配进入排序主体。

**仍然保留 Feed 的治理思想**：用「未授权赛事不参与打分排序」来实现对个性化作用范围的有界约束
（即上游计划 §3.6 的 B11），而不是用系数去限制。

### D-C 启动门禁：shadow 优先，不阻塞工程

沿用 FEED-5 的判定：

```
工程完成（含 trace / shadow / flag）        → 可合入
真实有效曝光 ≥500 且 加入计划 ≥30           → 解锁 active rollout（灰度）
```

在达到第二个条件前，**shadow 模式（percent=0）持续运行**：算分、记 trace、不改用户可见顺序。

### D-D 评估口径：没有曝光分母，就必须先造分母

**决策：把埋点（曝光 + 点击）作为与算法实现同等优先级的交付项，不做「先上算法后补埋点」。**

理由：上游计划的验收标准（Top10 中 major_match ≥70%）是**可离线算**的，
不需要线上数据；但 `major_hit_top10` 只说明「算法按设计工作了」，不说明「用户更满意了」。
要回答后者，必须有 CTR / 加入转化率，两者都需要曝光分母。

### D-E 探索槽：竞赛比 Feed 更需要

**决策：结果页保留约 15% 探索槽。** 理由见 §7.3（专业匹配会天然屏蔽高价值跨专业赛事）。

## 3. 核心算法选型与理由（对应需求第 2 点）

### 3.1 选型

**规则簇匹配（Rule-based Cluster Matching） + 加权线性打分（Weighted Linear Scoring） + 混合槽位排序（Slot-based Ranking）**

三层结构，每层都可独立测试与替换：

```
Layer 1  Eligibility Gates      硬门：治理 / 年级 / 截止
Layer 2  Match & Score          专业簇交集 + 五维加权打分 → match_score 0~100
Layer 3  Ranking & Slots        打分排序 + 探索槽 + 已加入惩罚
```

### 3.2 为什么是「专业簇交集」而不是文本相似度

旧实现用 `strings.Contains(赛事全文, 用户专业)`（`competition_preference_matching.go:139-148`），
这是本次故障的直接成因之一：全字段拼接文本做子串匹配，既漏（口径不同）又错（噪声命中）。

替代方案对比：

| 方案 | 判决 | 理由 |
|---|---|---|
| 全文字符串包含 | ✗ 已证实失败 | 口径不同导致漏召；拼接文本导致误召 |
| 编辑距离 / 模糊匹配 | ✗ | 「计算机类」vs「计算机科学与技术」编辑距离很远，「工业设计」vs「环境设计」很近 —— 与真实关系不符 |
| 词向量 / Embedding 相似度 | ✗ | 需要模型服务、不可离线复算、引入不确定性；且 53 个标签的闭集问题用不到它 |
| **闭集簇标签精确交集** | ✓ | 词表闭集（53 项）、关系由人工确定、结果完全确定、可离线复算、零推理成本 |

关键设计：**词典是双向可解析的**。

```
赛事侧 resolveEventClusters(eligible_majors):
   每个值 → 若本身是簇标签，取自身
           若是标准专业名，取其映射的簇
           都不可识别 → 记入 unknown_label 清单（不参与匹配，但必须可见）
用户侧 resolveUserClusters(edu_major):
   标准专业名 → 簇集合（含 override 优先）
```

这让引擎**同时兼容两种标注口径**（目录新包用簇标签，legacy 数据可能用标准专业名），
不需要在数据侧做一次性语法迁移。

### 3.3 为什么是可加线性模型而不是树模型

- 可加模型的每一项都能单独解释（`score_breakdown`），直接映射到用户可见的「匹配明细」；
  树模型的解释要靠 SHAP，成本与不透明度都不可接受。
- 权重可人工设定与调整，**可审计**（评审人能看到「专业匹配占 46 分」并质疑它）。
- 满分 100 的分档（高度匹配 / 较为匹配 / 可以探索）需要可加性才能稳定。

树模型的正确用武之地在 §6.6：**用它来校准权重，而不是替代线性形式。**

**P1 只用 F1–F20**（全部已存在）。F21 在埋点落地后并入。
**明确不做**（避免死分量，遵循 `feed5-personalized-design.md:85`）：
不做协同过滤交互矩阵、不做用户-用户相似度、不做赛事-赛事相似度。
这些在 310 条规模下没有统计意义。

### 4.2 特征计算的位置

遵循 `home_feed_ranker.go` 的惯例：**打分器是纯函数，不碰 DB**。

```
competitionmatching 包（新增，纯函数，无 DB/HTTP 依赖）
  ├─ vocabulary.go   簇词表 + 标准专业 → 簇 种子映射 + 别名归一
  ├─ resolve.go      resolveEventClusters / resolveUserClusters
  ├─ score.go        ScoreCandidate(...) → MatchResult{Score, Basis, Breakdown, Reasons}
  └─ rank.go         排序 + 探索槽 + 稳定 tie-break
```

引擎（`competition_candidate_engine.go`）负责从 DB 取特征、调纯函数、组装 DTO。
**这样打分逻辑可以离线用 JSON 输入复算，与线上完全一致** —— 这是黄金用例可验证的前提。

## 5. 打分模型

### 5.1 总分构成（满分 100）

```
match_score = M + P + G + T + V − Penalty     （clamp 到 0..100）
```

| 分量 | 上限 | 规则 |
|---|---|---|
| **M 专业匹配** | 46 | 簇交集命中 40；学院命中 26；tag/类别桥接 16；纯通用 8（**互斥取最高，不叠加**）；赛事 `eligible_majors` 直接含用户标准专业全名再 +6 |
| **P 偏好** | 22 | 方向 8/个（≤12）、技能 4/个（≤8）、角色 5/个（≤10），合计封顶 22 |
| **G 目标** | 12 | resume / postgraduate 看评级与学校认定；ability 看是否命中方向；exploration 恒定给分 |
| **T 时间** | 10 | `weekly_hours ≥ 估计投入` 给 8；长期训练偏好一致给 4；封顶 10 |
| **V 价值** | 10 | `competition_rating` S/A=4、B+/B=2、B-/C=1；`importance_score` ≥80 加 2、≥50 加 1；封顶 10 |
| **Penalty** | −15 | 时间待核实 −4；已截止 −8；高风险投入且用户投入偏低 −6；证据等级 B2 −3；已加入计划 −10 |

**M 的互斥设计是刻意的**：叠加会让「既命中专业又命中学院」的赛事被双重奖励，
而学院命中本身就是弱信号（一个学院多个专业）。

**V 的上限压到 10 分是治理要求**：`competition_rating` 是人工评级，
必须与「匹配度」严格分野，不能让高评级赛事靠评级压过专业匹配
（对应上游 §3.5 的命名强制要求）。

### 5.2 分档

| 分值 | `match_tier` | 文案 |
|---|---|---|
| ≥ 72 | `strong` | 高度匹配 |
| 55–71 | `suitable` | 较为匹配 |
| 40–54 | `explore` | 可以探索 |
| < 40 | 不进入「适合我」 | — |

### 5.3 权重性质声明

**以上权重是工程初始值，不是最优值，依赖 Rank Trace 调参。**
（照抄 `feed5-personalized-design.md:141` 的诚实标注。）
唯一有数据支撑的比例是 M 远大于 V —— 因为这是用户的原始诉求。

### 5.4 曝光惩罚的设计原则

沿用 `feed5-personalized-design.md:189-192` 的结论：

```
首次曝光未点击          → 0 penalty     （对新赛事公平）
≥2 个会话曝光且从未点击  → −6            （弱惩罚）
已加入计划              → −10 或置底     （强信号，但不是负反馈）
已参加（有对应 award）   → 置底           （避免推荐已完成的赛事）
```

**不做「曝光过就降权」的一刀切** —— 竞赛是窗口型内容，一次曝光未点击很可能只是时机不对，
一刀切会让新入库赛事永远无法出头。

### 5.5 排序与确定性

```
match_score DESC
  → competition_rating 序（S>A>B+>B>B->C）
  → importance_score DESC
  → catalog_order ASC
  → competition_id ASC
  → id ASC                    （最终稳定兜底）
```

**未授权赛事（`personalized_ranking_allowed=false`）不参与打分排序。**
若本次请求聚合后 `Catalog.PersonalizedRankingAllowed == false`，则整体回退纯 `catalog_order` ——
这保证了既有治理测试 `TestCompetitionCandidateEngineUsesCatalogOrderWithoutImportanceOrDeadlinePriority`
所断言的行为（重要度与截止不得改变目录序）继续成立。

## 6. 模型训练与评估指标（对应需求第 4 点）

### 6.1 澄清：「训练」在本场景的含义

本方案 P1 没有可训练的模型（§2 D-A 已论证）。
因此「训练」被拆成三件可执行的事：

1. **权重设定**（P1，人工 + 领域推理）—— 已给初始值
2. **权重校准**（P2，有标签后）—— 用逻辑回归拟合「是否加入计划」
3. **排序质量评估**（P1 起，离线 + 在线）

### 6.2 离线评估（P1 即可执行，不需要线上数据）

在固定目录快照 + 固定画像集上离线复算，指标：

| 指标 | 定义 | 目标 |
|---|---|---|
| `major_hit_top10` | Top10 中 `match_basis=major_cluster` 占比 | ≥ 70% |
| `recall@20`（按学院分层） | 每学院随机抽样专业，Top20 覆盖该专业应见赛事的比例 | ≥ 60% |
| `召回下限` | **每个专业至少有 N 条专业相关召回**（替换原「召回均衡度」指标） | ≥ 20 |
| `coverage` | 被至少一次推荐命中的赛事占全部候选池比例（**考察是否总推同一批**） | ≥ 60% |
| `zero_result_rate` | 空结果请求占比 | < 5% |
| `determinism` | 同输入重复计算的顺序一致性 | 100% |

> **指标修正（由实测证伪）**：原定的「四类专业召回量差异 ≤ 30%」**不可达且不应作为目标**。
> 实测显示目录本身的供给就是不平衡的——面向「计算机类」开放的赛事有 81 条，
> 面向「英语」的只有 29 条。要求召回量比值 ≤1.30 等于要求算法制造人为均衡，
> 而均衡的正确判据是**用户实际看到的首屏是否有足够的相关赛事**，不是池子大小相等。
> 实测已证明这一点：8 个专业在授权态下**首屏专业相关占比全部为 9/10**，
> 体验完全均衡，尽管召回量从 25 到 71 不等。因此该指标改为「召回下限 ≥ 20」。

`coverage` 是容易被忽略但很关键的指标：如果没有它，一个把 20 条固定赛事推给所有人的
「算法」也能拿到 100% 的 `major_hit_top10`（只要那 20 条标了专业）。

### 6.3 在线评估（需要埋点）

| 指标 | 定义 | 用途 |
|---|---|---|
| `CTR` | `calendar_add / impressions` 按 `algorithm_version` 切分 | 主指标 |
| `match_reason_open_rate` | 点开「为什么推荐」的比例 | 解释可信度代理指标 |
| `precision@5 加入率` | Top5 曝光中最终加入计划的比例 | 头部质量 |
| `negative_rate` | 「不感兴趣」/ 隐藏 占曝光比 | 健康度 |
| `explore_slot_ctr` vs `normal_slot_ctr` | 探索槽与常规槽对比 | 验证探索是否有效，或专业过滤是否过窄 |

### 6.4 校准方法（P2，门禁达标后）

当满足「有效曝光 ≥500 且加入计划 ≥30」时：

- **标签**：`y = 1` 若该赛事在曝光后 N 天内被加入计划。
- **分母**：曝光（必须有），否则只能做「已加入 vs 未加入」的偏差样本。
- **模型**：逻辑回归（可解释、系数即权重），特征 = §5.1 的五个分量 + 若干交互项。
- **产出**：用拟合系数**替换** §5.1 的人工权重，保持同样的可加线性形式。
- **守卫**：系数上线前必须过 §6.2 的离线指标，且 `coverage` 与 `召回均衡度` 不得劣化。
  防止模型把权重全压到「专业精确命中」上从而压缩覆盖率。

若逻辑回归仍不足（如发现强非线性），再考虑 GBDT + 单调约束，
但**必须保留 `score_breakdown` 的可解释输出**，否则会与治理要求冲突。

### 6.5 灰度判据

沿用 FEED-5 形状（`feed5-personalized-design.md:299`）：

```
[ ] 工程完成（打分 / 排序 / 探索槽 / trace / shadow / flag）
[ ] 真实有效曝光 ≥500 + 加入计划 ≥30     ← 只阻塞 active rollout，不阻塞 shadow
[ ] 离线指标 6.2 全部达标
[ ] ADR 评审通过（上游 §12 E1）
```

### 6.6 演进路线

```
P1  规则打分 + 人工权重 + shadow + trace     ← 本方案
P2  逻辑回归校准权重（同架构，只换系数）
P3  若数据量足够（曝光 ≥ 10^4），评估 LTR / 双塔；仅当 P2 明显不足时才做
```

**P3 大概率不需要。** 310 条物品的排序问题，规则法在可解释性和确定性上的收益
远大于一个模型带来的边际提升。诚实的预期管理比追求算法复杂度更有价值。

## 7. 冷启动与实时更新策略（对应需求第 5 点）

### 7.1 用户冷启动（三种状态，分别有明确行为）

| 状态 | 判定 | 行为 |
|---|---|---|
| 未登录 | `!isLoggedIn` | 「适合我」tab 不展示（现状已如此，保持） |
| 未核验身份 | `ProfileReady == false` | 返回 `reason_code=profile_incomplete` + 缺失字段清单；前端给引导入口（上游 F1/F3）；**不静默置空** |
| 已核验但无偏好 | `PreferenceConfigured == false` | P/G/T 计 0，M 与 V 照常；结果**照常返回**（偏好是可选增强） |

**关键：已核验但没填偏好的用户必须能看到结果。** 旧实现对这类用户虽然能出结果，
但因为在同一个池子里表现不好，掩盖了真正的问题。

### 7.2 赛事冷启动

**结构性免疫**。内容基打分只依赖赛事自身属性（开放专业 / 学院 / 标签 / 评级），
新赛事一入库即可被正确排序，不需要任何历史交互。

唯一的辅助信号是「已曝光次数」（F21），而它只在埋点落地后才参与，且按 §5.4 只做弱惩罚。

### 7.3 探索（防过滤气泡）

**这是竞赛模块比 Feed 更需要探索的原因**：

`eligible_majors` 为空的 35 条赛事（含「挑战杯」「中国国际大学生创新大赛」等
**全校最高价值赛事**）只能落进 `general_match`。而一个专业匹配打分高的学生，
`major_match` 池里已经有 60+ 条，`general_match` 会被压到很后面 ——
**结果是：最值得参加的跨专业顶级赛事，专业匹配越强的学生越看不到。**

这是纯 exploit 排序的结构性缺陷，必须用探索槽修正：

```
结果页 20 条中保留 3 条探索槽
  槽位：第 8、13、19 位（避开头部，避免干扰主判断）
  来源：general_match 池中 competition_rating 最高的未曝光赛事
  规则：探索槽不参与 match_score 排序，直接按价值评级占位
```

该设计同时服务两个目标：给高价值跨专业赛事曝光、给算法收集反事实数据（§6.4 需要）。

### 7.4 实时更新

| 变化 | 生效方式 | 延迟 |
|---|---|---|
| 用户偏好修改 | 请求时实时读 `user_competition_preferences` | 立即 |
| 专业簇 override | 请求时实时读 | 立即 |
| 学业身份变更（专业/学院/年级） | 请求时实时读 `users` | 立即 |
| 加入计划 | 下一次请求即体现惩罚 | 立即 |
| 目录变更 | 目录包 activate 时整体替换 | 分钟级 |
| 权重调整 | 配置化，不改代码 | 重启/热加载 |
| 学到的模型系数 | 周期性重训（周/月），版本化上线 | 天级 |

**P1 不需要任何缓存或在线学习**：310 条全量载入内存打分，单请求成本是微秒级。
过早引入缓存只会制造「缓存与画像不一致」这一新的 bug 来源。

## 8. 性能与可扩展性（对应需求第 6 点）

### 8.1 当前量级

| 环节 | 复杂度 | 实测预期 |
|---|---|---|
| DB 查询 | 1 次（治理门 + 筛选），310 行 | < 20ms |
| 画像读取 | 3 次小查询（user / preference / awards） | < 10ms |
| 打分 | O(N × 簇交集)，N=310，簇集合 ≤5 | < 2ms |
| 排序 | O(N log N) | < 1ms |
| 合计 | — | **P95 ≤ 600ms 的预算非常宽松** |

**结论：不需要索引优化、不需要缓存、不需要分片。**
唯一需要的新索引是 `academic_majors(normalized_name)` unique。

### 8.2 扩展性边界

| 规模 | 策略 |
|---|---|
| ≤ 2,000 条 | 维持现状（全量内存打分） |
| 2,000–20,000 条 | 把簇交集下推到 DB（`eligible_majors` JSON 包含查询 + 索引），先过滤再打分 |
| > 20,000 条 | 才需要考虑预计算倒排或引入检索层。**当前不需要，也不要提前做** |

物品数增长是**线性**影响打分阶段，而打分本身 < 2ms，所以真实瓶颈远未到来。
真正的扩展性风险不在算法，而在 §9 的数据治理（标签质量随规模下降）。

### 8.3 需要避免的性能反模式

- ❌ 逐候选查 DB（Feed 明确禁止：`feed5-personalized-design.md:94`「禁止 500 候选 × 每候选查一次 DB」）
  → 画像与已加入计划必须**一次查询聚合为 map**
- ❌ 在打分链路里做字符串模糊匹配（旧实现的错误）
- ❌ 为「算法感」引入向量检索 / 外部模型服务

## 9. 潜在的权衡与风险（对应需求第 7 点）

### 9.1 明确的权衡

| 权衡 | 选择 | 代价（承认） |
|---|---|---|
| 可解释 vs 精度 | 选可解释 | 放弃可能存在的非线性提升 |
| 确定性 vs 个性化 | 选确定性 | 无法做实时个性化探索（如 contextual bandit） |
| 专业主导 vs 价值曝光 | 专业主导 + 15% 探索槽 | 探索槽占用 3 个位置，头部精度略降 |
| 覆盖全校 vs 专业深耕 | 覆盖全校（均衡度 ≤1.3 为验收） | 无法为个别专业做超精细排序 |
| 单向归一化 vs 目录整改 | 画像侧归一化 | 目录 15 个模糊标签的噪声本期保留 |

### 9.2 风险清单

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **映射表质量决定一切** | 映射错 → 推荐错，且看起来「算法不工作」 | 教务名册复核 + `major_cluster_override` + 覆盖率报告让缺口可见 |
| R2 | 目录标签 15 个模糊样本（「数字媒体相关」等） | 一个宽标签命中大量赛事，虚高 | 宽标签在 M 分上打折；D3 目录修复时收敛 |
| R3 | 无曝光分母前的「成功」是自证的 | 离线指标达标 ≠ 用户满意 | D-D：埋点与算法同优先级；不上线未验证的乐观结论 |
| R4 | 反馈环（高分赛事获得更多曝光 → 数据更支持它） | 长期同质化 | 探索槽 + `coverage` 指标 + 已曝光惩罚（弱） |
| R5 | `competition_rating` 与 `match_score` 被混淆 | 治理违规 + 用户误解 | 命名强制分隔 + 前端分区展示 + 治理断言测试 |
| R6 | 权重是拍脑袋的 | 调参无依据 | 明确标注为初始值（§5.3）+ Rank Trace 5% 采样 |
| R7 | 灰度期间授权赛事与未授权赛事混排 | 顺序语义不一致 | §5.5：聚合门为 false 时整体回退目录序 |
| R8 | 专业映射成为单点（一人维护） | 人员变动即失修 | 映射表入库（非硬编码）+ 覆盖率报告纳入例行检查 |

### 9.3 明确不做的事（防止范围蔓延）

- 不做深度学习排序、不做 embedding 召回
- 不做实时个性化（contextual bandit / 在线学习）
- 不做跨校数据、不做社交关系推荐
- 不做「获奖概率」预测（治理明确禁止，且无数据支撑）

## 11. 实测验证结果（已执行，非预测）

用 `server/cmd/matchingverify` 对真实目录快照（`tmp/competition-schedule/public-events.json`，
310 条已发布赛事）复算。**该工具直接调用线上同一份 `competitionmatching` 纯函数包**，
因此离线结果与线上必然一致——不存在「离线脚本另写一套逻辑」的漂移。

```powershell
go run ./cmd/matchingverify -catalog ../tmp/competition-schedule/public-events.json
go run ./cmd/matchingverify -catalog ../tmp/competition-schedule/public-events.json -assume-authorized
```

### 11.1 召回修复效果（对照上游计划 §1.3 的基线）

| 专业 | 基线 major_match | 修复后 major_match | 基线被丢弃 | 修复后被丢弃 |
|---|---|---|---|---|
| 计算机科学与技术 | **0** | **71** | 272 | 47 |
| 自动化 | **0** | **31** | 279 | 47 |
| 机械设计制造及其自动化 | **0** | **44** | 277 | 47 |
| 工业设计 | 60 | 60 | 219 | 47 |
| 环境设计 | 34 | 34 | 245 | 47 |
| 会计学 | 25 | 25 | 249 | 47 |
| 英语 | 25 | 25 | 254 | 47 |

- **三个主线专业的 major_match 从 0 提升到 31–71**，达到并超过验收下限。
- **被丢弃数从 219–279 降至统一的 47**，且这 47 条全部是**年级门真实不符**（目录中 47 条带
  `eligible_entry_years`，如「研究生」类赛事），不再是「专业标注越全越被淘汰」。
- **53 个目录标签全部可解析，未识别标签为 0**，说明目录侧无需语法迁移。
- **确定性自检通过**：263 条候选 5 次重复计算顺序完全一致。

### 11.2 用户可见效果取决于目录授权（**关键发现**）

首屏 Top10 中「专业直接相关」的占比：

| 状态 | 8 个专业的首屏专业相关占比 | 说明 |
|---|---|---|
| **现状**（`personalized_ranking_allowed` = 0/310） | **0–3 / 10** | 排序按治理约束回退纯目录序 |
| **模拟阶段 2**（`-assume-authorized`，全授权） | **9 / 10（全部 8 个专业一致）** | 达标，且各专业体验完全均衡 |

**结论：召回修复是必要但不充分的。** 算法本身已证明有效（90% ≥ 70% 门槛，且不挑专业），
但**只要目录尚未授权个性化排序，用户看到的首屏就仍然是目录序**，改善为零。
这正是上游计划 §0.1 D1 所识别的前置决策，此处被量化证实。

**因此阶段 1 上线后应预期「分组正确、首屏未变」，不要把首屏未改善误判为算法失败。**

### 11.3 被证伪的验收标准

原定「四类专业召回量差异 ≤ 30%」实测为 **2.84**，不可达。原因不是算法，
而是目录供给本身不平衡（面向「计算机类」81 条 vs 面向「英语」29 条）。
但同一份实测显示 8 个专业的首屏专业相关占比**全部为 9/10**——真实体验是均衡的。
故该指标已在 §6.2 替换为「召回下限 ≥ 20」。

### 11.4 仍需处理的事项

| 编号 | 事项 | 证据 |
|---|---|---|
| V1 | 47 条赛事因年级门被淘汰，需确认是否均为「研究生」等真实不适配 | 每个专业被淘汰数恒为 47 |
| V2 | 覆盖率审计脚本尚未输出「哪些标准专业无映射」清单 | 需接入教务名册后重跑 |
| V3 | 首屏效果待目录授权后方可验收 | §11.2 |
