## 已实现

1. Web 请求和自动刷新固定发送 `X-Auth-Transport: cookie`，调用方不能改为 Bearer。后端原生客户端响应契约保留。
2. 邮箱重置、历史教务找回和邮箱更新使用一致的账号键与持久化清理方法。只清理经过实际登录解析确认归属的标识，同时清理数据库故障时产生的内存回退计数；来源 IP、其他账号和歧义别名不解锁。
3. 成功登录写逐条 `login_success` 审计以及安全中心聚合事件。来源、UA、安装标识、会话族使用 HMAC 摘要；普通新设备为观察记录，管理员新设备进入高危告警通道。新设备判定依赖可伪造指纹，不等于抗钓鱼认证。
4. 将已有但未接入的 `BrowserOriginGuard` 接入主路由，支持精确配置的可信 Web Origin，保留原生无 Origin 请求，并拒绝跨站、缺 Origin 的同站子域和畸形 Origin 写请求。
5. 增加 systemd 的 30r/m 登录 dry-run 配置片段。Docker 专用登录 zone 保留原有 30r/s、burst=60 防洪预算，返回 429；未静默取消已有防护。
6. Go 最低版本升到 1.26.9，`x/net` 升到 0.60.0 及其必要关联依赖；另修复 edwards25519、protobuf 的已知依赖公告。Docker、部署脚本、版本说明及资产测试同步更新。
7. 成功登录逐条流水按 90 天清理，其他安全审计操作沿用原策略；更新隐私与留存台账。
8. 修正全量门禁中发现的既有测试夹具：食堂今日数据在午夜跨日、重复运行时内存数据库残留；AI 测试的 SQLite 锁争用和异步取消观察时序。保留原业务断言，未改变 AI 或食堂业务代码。

运行配置和恢复入口见 [登录安全运维文档](../ops/auth-security.md)。

## 生产核查和证据

生产为 Nginx + systemd，Go 以 `shenliyuan` 用户运行。Go 8080、PostgreSQL 5432 和内部 Python 服务绑定回环地址；UFW 当前 inactive，未核验云侧安全组。`nginx -t`、业务 health 和 version 正常。时区 Asia/Shanghai，NTP 同步开启，与本次调查使用的 UTC+08 一致。

Go 信任 `127.0.0.1/32`，生产来源封禁为 false，安全表就绪。Nginx 当前未配置接口限流，代理仍追加 XFF。本地测试确认该信任边界不会接受直连伪造 XFF 或追加链左侧的伪造来源；两个真实公网出口与 CDN 拓扑尚未实测，不能仅根据数据库的归因有效字段确认来源身份。

应用数据库连接账号为 `postgres`，数据库查询确认该角色具有超级用户、建库和建角色权限。应用与迁移账号拆分仍需专项兼容改造；本轮未直接撤销生产权限。SSH 密码认证开启，root 仅允许非密码认证。

真实用户链路：测试账号先触发邮箱、QQ、历史别名持久化锁定，再发送夹具验证码并重置密码；新密码从三个入口立即登录成功，旧密码、旧访问令牌和旧刷新会话拒绝，其他账号与来源锁定保留。无效验证码不会修改密码、会话或锁定。该链路在 SQLite 与隔离 PostgreSQL 执行，真实生产账号链路仍待发布后验收。
